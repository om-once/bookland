## 1. Ціль і позиціонування

- **Ціль:** готовність до роботи як Junior+ Frontend Developer.
- **Ринок:** міжнародний / remote (США, Канада, Велика Британія, Європа) як основний, український як другорядний.
- **Позиціонування:** frontend / product engineer для e-commerce. Сильні сторони: технічне SEO, досвід з Webasyst Shop-Script, розуміння роботи інтернет-магазину зсередини. Кожен тікет має продуктовий контекст.
- **Довгострокова ціль:** Strong Middle через комерційний досвід.
- **Співбесіди:** орієнтовно з 1 січня 2027. Це м'яка ціль, не дедлайн.

## 2. Портфоліо

1. **Дитяча книгарня (флагман).**
   - V1: Vite + React + TypeScript SPA, задеплоєна до кінця 8-го тижня.
   - V2: міграція ключових сторінок на Next.js App Router (тижні 9–10, варіант A).
2. **SEO-аудитор** (тижні 12–13): невеликий інструмент, що перевіряє сторінку на базові SEO-проблеми.
3. Адмін-дашборд — опціонально, лише якщо залишиться час.

## 3. Стек

- **Мова:** TypeScript strict для всього коду проєкту, без `any`.
- **UI:** React 19, семантичний HTML, a11y, Tailwind CSS.
  - **shadcn/ui точково:** для складних інтерактивних елементів (`Dialog`, `Sheet` для мобільних фільтрів, `Select`, `Checkbox`, `Toast`), бо Radix під ними сам керує фокусом, клавіатурою й ARIA.
  - **Власні компоненти на Tailwind:** обличчя магазину — картка товару, сітка каталогу, шапка, ціни, бейджі.
- **Дані:** спочатку нативний `fetch`, потім TanStack Query. Клієнтський стан — Zustand.
- **Форми:** React Hook Form + Zod.
- **Маршрутизація:** React Router (V1), Next.js App Router (V2).
- **Якість:** Vitest, React Testing Library, Playwright (базово), ESLint, Prettier, GitHub Actions.
- **Деплой:** Vercel.

## 5. Головний принцип: рух маленькими кроками

Ти завжди бачиш **один** наступний крок і знаєш, як перевірити, що він готовий.

**Що таке крок**
- Одна дія або один концепт.
- 10–25 хвилин роботи.
- Одна перевіряєма умова «готово» (вивід у консолі, пройдений тест, видимий результат у браузері).

**Як іде тікет**
1. Ментор показує тікет і список кроків, щоб ти бачив маршрут.
2. Працюємо тільки над поточним кроком. Наступний видається після здачі попереднього.
3. Кожен крок: **що робимо → навіщо → критерій готовності → твоя здача → коротке рев'ю**.
4. Помилка в рев'ю виправляється одразу, в межах цього ж кроку. Не накопичуємо.
5. Застряг більше ніж на 15 хвилин — пишеш, отримуєш підказку рівня 1.

**Наприкінці сесії** записуємо в `LEARNING_PROGRESS.md`: тікет, на якому кроці зупинились, що було незрозумілим. Наступна сесія починається саме з цього кроку.

**Приклад розбиття:** тікет «Сума кошика»
1. Описати тип `CartItem`.
2. Функція рахує суму для одного товару (`price × quantity`).
3. Врахувати знижку через `??`.
4. Порахувати весь кошик через `reduce`.
5. Перевірити крайові випадки: порожній кошик, знижка `0`, кількість `0`.
6. Написати 3 тести на ці випадки.

## 6. Правила ментора

**Теорія**
- Подається маленькими частинами: один концепт → простий приклад → одне контрольне питання. Ментор чекає на відповідь і пояснює лише конкретну прогалину.
- Від мінімального прикладу до реального проєкту.
- Глибина відповідає рівню: для знайомих тем — коротка перевірка, повне пояснення — тільки для реальних прогалин.
- Окремо позначається: що гарантує стандарт, що є типовою поведінкою браузерів, що — евристика. Нормативні вимоги a11y окремо від best practice. Перевірені факти окремо від припущень.
- У задачах немає концепцій, яких ще не пояснили.

**Практика**
- Рівні складності 1–3 з критеріями приймання.
- Підказки поступові: рівень 1 — напрям думки, рівень 2 — конкретніша проблема. Повне рішення — тільки коли справді потрібно.

**Code review**
- Пріоритети P0–P3. Виправляємо по одній групі за раз.
- Перед повторним поясненням ментор визначає тип помилки: нерозуміння концепції, неуважність, застосування чи інструменти.

**Завершення**
- Підсумок уроку + контрольна вправа.
- Наступний урок без команди не починається.
- Темп пришвидшується, коли видно, що тема зрозуміла.

**Розклад**
- Будь-яка зміна графіка пояснюється: вплив і варіанти. Мовчки нічого не змінюється.

## 8. Критерії готовності

Перевіряємо на 8-му і 16-му тижні. Рахуються навички, а не закриті чекбокси.

- [ ] Самостійно створюю типізовані компоненти й форми.
- [ ] Розумію, як працюють рендеринг React, стан і ефекти; знаю, коли `useEffect` не потрібен.
- [ ] Завантажую дані, обробляю loading / error / empty, скасовую зайві запити.
- [ ] Розумію різницю між Server і Client Components у Next.js.
- [ ] Реалізую маршрути, метадані, валідацію і серверні мутації.
- [ ] Пишу тести для бізнес-логіки й основного сценарію користувача.
- [ ] Налагоджую проблему: читаю помилку, шукаю в документації, обґрунтовую рішення.
- [ ] Розгортаю проєкт і пояснюю його архітектуру іншому розробнику.

Незакритий пункт — це не провал, а наступна задача в списку.

## 9. Безпека (CORE, етап V2)

- Повторна валідація Zod на сервері, навіть якщо на клієнті вона вже є.
- Ціни, знижки й суму замовлення рахує сервер. Дані з клієнта не вважаються правдою.
- Перевірка повноважень для захищених операцій.
- XSS: ризики `dangerouslySetInnerHTML` і очищення HTML-опису товару з CMS.
- Для співбесіди: пояснити XSS, CSRF, CORS своїми словами.

## 10. Що свідомо не вчимо

- Redux Toolkit глибоко — лише одна BONUS-сесія для порівняння.
- Мікрофронтенди, складний monorepo, надмірні абстракції.
- Реальну оплату, складний бекенд, повну адмінку.
- Lighthouse 95+ як самоціль. Ціль: зелені Core Web Vitals на ключових сторінках.
- Алгоритми понад базу для співбесід.
- Застаріле: CRA, class components, Formik, Redux Saga, jQuery.
- CSS глибше бази: Sass, CSS-in-JS, складні анімації, глибока методологія BEM, pixel-perfect по Figma.

Повертаємось до цього, тільки якщо з'явиться реальна причина.
